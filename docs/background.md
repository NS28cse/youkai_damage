## 1. Gemini での検討（2026-10 以前）

### Gemini②「スマートフォンカメラで数値認識」（全5往復、先に行われた会話）

- リンク: https://share.gemini.google/Z9C2khoYi7aY
- 流れ:
  1. 方法の比較: PC 画面の直接キャプチャ／キャプチャーボード／スマホカメラ撮影。Gemini は前の2つを推奨。
  2. オーナーが「キャプチャーできないゲーム機なのでスマホ撮影しかない」としてカメラ方式に決定（D1）。
  3. カメラ方式の具体案: 三脚で真正面に固定、部屋を暗くする、数字の出る領域を固定して OpenCV.js で前処理し Tesseract.js で読む、Node.js サーバー + SQLite。
  4. 同じフォントなので専用モデルを作れるか → Tesseract の独自学習の手順。
  5. TensorFlow ではどうか → CNN + RNN + CTC（CRNN）。Gemini の結論は「まず Tesseract、駄目なら TensorFlow」。

### Gemini①「スマホカメラでリアルタイム数値認識」（全16往復）

- リンク: https://share.gemini.google/zAspUjmipbJ8
- 流れ:
  - Turn 1〜4: 構想と要件（リアルタイム、Web 表示、CSV）。PC ではプレイできないためスマホカメラ必須（D1〜D3）。
  - Turn 5〜8: 開発環境（Colab で学習、PyCharm Pro でアプリ開発）（D8）。4種類の分類の要望（D4）。
  - Turn 9〜12: 深層学習での判別方法。キャラ追跡・行動認識を組み合わせる案（W2）から、1枚の画像に「種類 + 数値」だけをラベル付けする方針に収束（D5〜D7）。
  - Turn 13: ファイル命名規則とフォルダ構成（P12）。
  - Turn 14: 自己教師あり学習で事前学習し、少量のラベル付きデータで仕上げるハイブリッド案。
  - Turn 15: プレイ動画から OpenCV でフレームを切り出して学習データにできる。
  - Turn 16: 全体のまとめ。最終構成は「スマホ（HTML/JS）→ WebSocket/WebRTC → PC の FastAPI で推論 → 結果を返す」、公開は Render / Netlify / Vercel。

## 2. Claude による計画のレビュー（2026-10-29）

Gemini での計画を Claude がレビューした内容。結果は [decisions.md](decisions.md) の提案（P1〜P11）と取り下げ（W1）に反映済み。

### 良い点

- 大きな流れ（カメラ → AI 認識 → 表示 → CSV）は妥当。
- ラベルを「種類 + 数値」に絞り、モーション認識・キャラ追跡を外した判断は正しい。

### 重大な指摘

1. **重複除外が最終まとめから抜けている**（P2）: 数字は 0.5〜1 秒残るため、追跡なしでは1回のダメージが何行も記録される。
2. **推論の場所が矛盾している**（P1, P9）: 「推論は PC」としつつ公開先は Render（無料枠は GPU なし）。手元 PC の場合も、スマホのブラウザは HTTPS でないとカメラを使えないため、LAN 内の http では動かない。
3. **学習データと本番の見た目のずれ**: 本番は「カメラで画面を撮った映像」なので、学習データも同じカメラ配置で撮る必要がある。
4. **敵／味方を1枚で判別できるかが未検証**（P3, Q4）: 設計の中心となる前提。少量のラベル付けで早期に確認する。

### Gemini② の提案のうち採用しないほうがよいもの

- 領域を固定して Tesseract で読む方式: 数字の位置が毎回変わるダメージ数値には合わない（P4）。
- 「まず Tesseract」の順番: 紹介された学習手順は古い世代向けで、派手な背景上の色付き数字にも弱い（P4）。
- Node.js サーバー: Gemini① の FastAPI と食い違う（P8）。

### 中程度の指摘

- 自己教師あり学習はまだ早い。疑似ラベルのほうが現実的（P6）。
- TensorFlow より PyTorch 版 YOLO のほうが楽（P7）。
- 評価の基準（記録漏れ・余計な記録の割合）を先に決める。
