# 実現性検証（合成データ）

実施: 2026-10-30。実際のゲーム映像がまだないため、**合成データ**で「仕組みとして成り立つか」を確かめた。

## 何を確かめたか / 確かめていないか

| 確かめたこと | 方法 |
|---|---|
| 3DS 上画面をカメラで撮った解像度で、数字を検出して読めるか | 合成データで学習・評価 |
| 数字の大きさ（ネイティブ画素の高さ）で精度がどう変わるか | 高さ別に集計 |
| 色でダメージ／回復を分けられるか | 検出モデルの2クラス分類 |
| Colab CLI で学習を回せるか | 実際に T4 で実行 |
| スマホのブラウザでどれだけ速く動くか | 速度テストページ（`bench/`）をオーナーの Android で実行 |

**確かめていないこと**（実映像が必要）: 実際のゲームのフォント・エフェクト・背景での精度、敵／味方を1枚で判別できるか（Q4）、実際の LCD・カメラの見え方。

## 合成データ（`gen_synth.py`）

- 3DS 上画面（400×240）を模した画像に、ランダムな背景（図形・グラデーション）、紛らわしいもの（オレンジ／緑の丸、白い無関係な数字）、0〜4個の数字を描く。
- 数字: 値 1〜9999、オレンジ（ダメージ）か緑（回復）、縁取りあり、半透明（出現・消滅中）あり。高さ 8〜14 ネイティブ画素。フォントは DejaVu Sans Bold（**ゲームのフォントではない**）。
- カメラの再現: LCD の画素格子、画面が映像の高さの 80〜98% を占める配置、斜め（四隅 ±2%）、ぼけ、手ぶれ、色・明るさ・ガンマのずれ、映り込み、ノイズ、JPEG 圧縮。720p（1280×720）で出力。
- 枚数: 学習 3000 / 検証 400 / テスト 400。

## モデルと評価（`train_eval.py`）

- 検出: YOLO11n、入力 640、2クラス（damage / heal）、30エポック。
- 読み取り: 検出枠を切り抜き、YOLO11n（入力 192）で各桁（0〜9）を検出して左から並べる。
- 通し評価: テスト画像で「位置（IoU≥0.5）・種類・値」がすべて合ったものを正解とする。
- 左右反転の水増しは数字の形を壊すので無効にした。

## 再現方法

```bash
python gen_synth.py --out /content/synth --font DejaVuSans-Bold.ttf
EPOCHS=30 python train_eval.py /content/synth /content/out
bench/build.sh /content/out <出力先>   # 速度テストページの組み立て
```

Colab CLI での実行手順は [docs/dev_environment.md](../../docs/dev_environment.md) を参照。

## 結果（2026-10-30）

### 精度（合成テストデータ 400枚・数字 781個）

「位置・種類（ダメージ／回復）・値」がすべて正しいものを正解とした。

| 検出モデルの入力 | 再現率 | 適合率 | 高さ 8〜9px | 10〜11px | 12〜14px |
|---|---|---|---|---|---|
| 640（PyTorch, Colab） | 99.2% | 99.1% | 215/219 | 232/234 | 328/328 |
| 640（ONNX, `eval_onnx.py`） | 99.1% | 99.4% | 213/219 | 234/234 | 327/328 |
| 320（ONNX、640 で学習したモデルをそのまま使用） | 93.6% | 94.6% | 190/219 | 221/234 | 320/328 |

- 検出の mAP50 は 0.995（damage 0.995 / heal 0.994）。色によるダメージ／回復の区別で誤りはほぼない（781個中 3個）。
- 高さはネイティブ画素（3DS 上画面 400×240 での高さ）。
- 入力 320 で使うなら、320 で学習し直すか、画面部分だけを切り出す工夫が必要。

### 速度

ブラウザ（onnxruntime-web 1.30.0、WASM・CPU）で1フレームあたり「検出1回 + 読み取り2回」にかかる時間。計測はこの検証環境のデスクトップ CPU（ヘッドレス Chromium）で、**スマホの値ではない**。

| 条件 | 検出 640 | 検出 320 |
|---|---|---|
| 1スレッド | 391 ms（2.6 回/秒） | 155 ms（6.4 回/秒） |
| 4スレッド（要 COOP/COEP ヘッダー） | 144〜155 ms（6.5〜7.0 回/秒） | 56〜70 ms（14〜18 回/秒） |

- 複数スレッドを使うには、配信側で `Cross-Origin-Opener-Policy: same-origin` と `Cross-Origin-Embedder-Policy: require-corp` を付ける必要がある。WebGPU も未使用（使えばさらに速くなる可能性がある）。
- 3枚のサンプル画像では、ブラウザ上の結果が正解と完全に一致した。
- スマホでの実測は、速度テストページ（`bench/`、claude.ai の Artifact として公開: https://claude.ai/artifact/5DydNecvwWU6EyU4SsHdnG 、オーナーのみ閲覧可）で行う。公開先の制約で、1スレッド・WASM のみ（最も遅い条件）。

### 学習の費用

Colab T4 で学習 31分（データ生成を含めて約50分）。消費 0.79 コンピューティングユニット。

### 結論

- 合成データでは「検出 → 色で種類 → 読み取り」の仕組みは成り立つ。3DS 上画面の小さい数字（高さ 8px）でも 97% 読めた。
- ブラウザ内での推論は、デスクトップ CPU で毎秒 3〜7 回。数字は 0.5〜1 秒表示されるので、毎秒 3 回以上なら各数字を 1〜3 回は捉えられる。スマホの実測が必要。
- 実際のゲーム映像での精度と、敵／味方の判別（Q4）は未検証。次は実映像の試験収集（[データ収集計画](../../docs/data_collection_plan.md) のフェーズ1）。
